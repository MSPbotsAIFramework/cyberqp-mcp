## Requirement understanding

One line: Give MSPbots agents visibility into CyberQP privileged access management (PAM) through hard-scoped, read-only, non-credential-exposing tools.

CyberQP (vendor brand "QuickPass Cybersecurity") is a third-party PAM/PEDM product that MSPs use to manage privileged local-admin and service accounts, time-bound ("just-in-time") elevated access, and an audit trail of who touched what privileged account and when. The requester (Ken Lee) wants an MSPbots MCP connector so an agent can answer questions like "what privileged accounts exist for this customer", "which JIT access is currently active or about to expire", and "what privileged-access activity happened and who triggered it" — without the connector ever being able to retrieve an account's password, an OTP secret, or an enrollment/install token, and without it being able to create, enable, disable, or delete anything. Success is: those visibility questions are answerable through MCP tools, and the tool surface itself makes credential retrieval and mutation structurally impossible, not merely discouraged.

The ticket also links `https://conduit.wyre.ai/plugins/cyberqp` — a third-party MCP marketplace listing. This is a new-vendor, first-version build (`vendor-mcp-development` SOP "main line A"), not a bug fix or an addition to an existing connector.

## Product design

### Goals / Non-goals

**Goals**

- Read-only visibility into: the tenant's customers/clients, each customer's managed (privileged) accounts and their counts by type, JIT (time-bound privileged) accounts at both customer and tenant scope, JIT policies, an audit/event log of privileged-access activity, and basic tenant/company metadata.
- No tool in the server can return a CyberQP account password, an OTP secret, or an install/enrollment token.
- No tool in the server can create, update, enable, disable, or delete anything in CyberQP (no JIT account provisioning, no password rotation, no OTP management, no identity-verification push, no event submission).
- The "hard-scoped" requirement is met structurally: the forbidden capabilities are simply not implemented as tools, not implemented-and-gated.

**Non-goals**

- Retrieving or displaying any CyberQP-managed account password, OTP seed, or install/enrollment token — out of scope even though CyberQP's API technically offers these endpoints; see Tech design for the full list of excluded endpoints.
- Creating, enabling/disabling, or deleting JIT accounts; triggering an identity-verification push; submitting a generic event — out of scope, all are write/side-effecting operations.
- Credential/password rotation of any kind — out of scope; the connector never requests the `password_rotation_write` OAuth scope.
- Provisioning the CyberQP OAuth application or obtaining the initial access token — outside this server. A tenant's Primary/Super role holder consents through CyberQP's own dashboard flow (per CyberQP's "Getting started with the CyberQP API" guide); the MSPbots Connector gateway is responsible for injecting and refreshing that token per request, the same as every other OAuth2-based vendor connector on this platform.
- Automatic cross-page aggregation ("fetch every customer's accounts in one call") — each tool returns one page per call; the agent pages explicitly.

### Acceptance criteria AC1..AC15

- **AC1**: Given a valid CyberQP access token and base URL for a tenant, when the agent calls the "list customers" tool, then it returns the tenant's visible customers/clients (paginated, default `limit` ≤ 50), and no item in the response contains a password, OTP, or install-token field.
- **AC2**: Given a customer ID that exists for the tenant, when the agent calls the "list customer accounts" tool, then it returns that customer's managed accounts — id, display name, account type, enabled state — paginated (`hasMore`/`nextCursor`), with no password field on any item.
- **AC3**: Given a customer ID, when the agent calls the "get customer account counts" tool, then it returns the counts of accounts broken down by account type for that customer.
- **AC4**: Given a customer ID and an account type, when the agent calls the "list JIT policies" tool, then it returns the configured JIT policies (name, description, active flag, privileged groups, durations) with no credential material in any item.
- **AC5**: Given a customer ID, when the agent calls the "list customer JIT accounts" tool, then it returns that customer's current JIT (time-bound privileged) accounts, including enabled state and expiration, with no password or OTP field on any item.
- **AC6**: When the agent calls the "list tenant JIT accounts" tool with no customer filter, then it returns JIT accounts across the whole tenant, paginated the same way as AC5.
- **AC7**: Given a customer ID and a user type, when the agent calls the "check JIT account" tool, then it returns whether a JIT account currently exists for that customer/user type, as a boolean, with no credential field in the response either way.
- **AC8**: When the agent calls the "list events" tool with any combination of customer, account, event type, status, and date-range filters, then it returns the matching audit/event records (who triggered it, what happened, when, result status), paginated, with no credential field on any item.
- **AC9**: When the agent calls the "list event types" tool, then it returns the reference list of event-type codes usable as the `event_type` filter in AC8.
- **AC10**: When the agent calls the "get tenant company data" tool, then it returns the tenant's CyberQP company/account metadata (name, identifiers) used to confirm which CyberQP tenant the supplied credential is scoped to.
- **AC11**: Given a request to `/mcp` that is missing either required credential header, when any tool is invoked, then the server returns HTTP 401 before making any call to CyberQP, and the body names every missing header.
- **AC12**: Given a CyberQP access token that CyberQP itself rejects as invalid or expired (upstream 401/403), when any tool is invoked, then the tool returns the structured error envelope with `code="unauthorized"`, `retryable=false` — never a stack trace, and never the raw CyberQP response body in `message`. The same envelope pattern applies to `rate_limited` (upstream 429, `retryable=true`) and `upstream_error` (upstream 5xx or network timeout, `retryable=true`).
- **AC13**: When a query legitimately matches zero records (e.g. a customer with no accounts, or an event-log filter with no hits), then the tool returns an empty `data` list as a normal successful result, never an error.
- **AC14**: Given a customer ID (or other single-resource ID) that does not exist for the tenant, when the agent calls a per-ID tool, then it returns `code="not_found"`, `retryable=false`.
- **AC15**: The complete set of tools exposed by this server is exactly the 10 read-only tools enumerated in Tech design § Data & API contract — no tool exists (even disabled or flagged) that can retrieve a password/OTP/install-token, or create/update/enable/disable/delete a CyberQP resource.

### Open questions

- **Q1 [non-blocking]**: `GET /api/v1/customers` requires a `directoryType` query parameter, and `accountType`/`userType` values are typed `string` in the fetched spec rather than a closed `enum` — the exact value set isn't fully enumerated in the spec snapshot taken for this design. Assumption: the dev leg exposes `directory_type` (and the other type filters) as plain string parameters, pulling the authoritative accepted values from the live spec or CyberQP's own docs at implementation time, and documents whatever it finds in the tool's `description`. Not blocking: worst case is a slightly under-specified parameter description, not a wrong capability.
- **Q2 [non-blocking]**: Multi-region base URL — a request to the wrong regional host will 401 even with an otherwise-valid token. Assumption (recorded as a decision below, not left to the dev leg to improvise): `X-CyberQp-Base-Url` is a **required** header with no default, so a tenant configured for the wrong region fails loudly and immediately rather than silently querying another region's (empty, for that tenant) data.

## Tech design

### Conclusion

Build the first version of `MSPbotsAIFramework/cyberqp-mcp` as a stateless MCP Streamable-HTTP server (Python + FastMCP, per the SOP's reference implementation) exposing exactly 10 read-only tools that wrap 9 of CyberQP's 25 public REST endpoints plus one reference-data endpoint. Every endpoint that returns a password, OTP secret, or install/enrollment token, or that performs a write, is simply not wrapped — the "hard-scoped, read-only, non-credential-exposing" requirement is satisfied by the tool inventory itself, not by a runtime flag.

### Where the current implementation lives

Nothing exists yet beyond the two-line `README.md` at `1e9be1e` on `main`. This is a from-scratch build (SOP main line A), not a modification.

### Option analysis

- **Language/framework**: Python + FastMCP + `httpx` + `pydantic` (+ `pydantic-settings` with `SettingsConfigDict(extra="ignore")` per SOP §1.2), matching the SOP's own recommended implementation and the stack already used across sibling repos in `MSPbotsAIFramework` (e.g. the Exchange Online connector). No project-specific reason to pick Node/TypeScript instead.
- **Tool granularity**: one tool per genuinely distinct query shape (SOP §2.1 "capability, not endpoint mirror") rather than one tool per raw endpoint. The 9 read endpoints selected each already represent a distinct business question (customers, per-customer accounts, per-customer account counts, JIT policies, per-customer JIT accounts, tenant-wide JIT accounts, JIT existence check, events, event types) plus tenant metadata — 10 tools total, comfortably under the SOP's "≤ 20" guideline, so no forced merging was needed. The alternative of merging `list_customer_jit_accounts` and `list_tenant_jit_accounts` into one tool with an optional `customer_id` was considered and rejected: the two map to different CyberQP paths with different parameter shapes (`searchText`/`limit`/`page` vs. the same plus a required path segment), and keeping them separate matches the vendor's own API shape more directly for an Agent reading the tool `description`.
- **Error handling**: structured in-band JSON error envelope (SOP §4.1/§4.2) rather than raising MCP-protocol-level errors — matches the SOP's own rationale (easier for the Agent to branch on `code`/`retryable` without the call chain being interrupted) and is the pattern already used by sibling connectors.

### Data & API contract

**Credential headers** (SOP §3.1 naming format `X-<Vendor>-<Credential>`; final table to ship verbatim in `README.md`):

| Header | Required | Meaning | Where to get it |
|---|---|---|---|
| `X-CyberQp-Access-Token` | Yes | OAuth2 bearer access token for the tenant's CyberQP account. Request only the `profile` and `customer` scopes — **never** `password_rotation_write`, since this connector has no write tools. | A tenant's Primary or Super role holder generates it via CyberQP's API consent flow — see "Getting started with the CyberQP API" on CyberQP's support site. Expires hourly; refreshed by the MSPbots Connector gateway, not by this server. |
| `X-CyberQp-Base-Url` | Yes | The tenant's CyberQP regional API host, e.g. `https://ca.cyberqp.com`, `https://us.getquickpass.com`, or `https://eu.getquickpass.com`. No default — see Decisions below. | Matches the host the tenant already uses to log into the CyberQP dashboard. |

**Tool inventory (10 tools, all `readOnlyHint=true`, none `destructiveHint`):**

1. `cyberqp_list_customers(name: str | None, directory_type: str, limit: int = 50, page: int | None)` → `{"data": [{"id", "name", "directoryType", ...}], "totalItems"}` — wraps `GET /api/v1/customers`.
2. `cyberqp_list_customer_accounts(customer_id: str, account_type: str | None, limit: int = 50, cursor: str | None)` → `{"data": [{"id", "displayName", "userPrincipalName", "samAccountName", "email", "accountType", "userType", "enabled"}], "hasMore", "nextCursor"}` — wraps `GET /api/v1/customers/{id}/accounts`. No password field exists anywhere in the upstream `CustomerAccountsList` schema.
3. `cyberqp_get_customer_account_counts(customer_id: str)` → `{"data": {"<accountType>": <count>, ...}}` — wraps `GET /api/v1/customers/{id}/accounts/count`.
4. `cyberqp_list_jit_policies(customer_id: str, account_type: str)` → `{"data": [{"id", "name", "description", "active", "privilegedGroups", "durations"}], "maxCount"}` — wraps `GET /api/v1/jit-policies/account`.
5. `cyberqp_list_customer_jit_accounts(customer_id: str, search_text: str | None, limit: int = 50, page: int | None)` → `{"data": [{"id", "displayName", "username", "accountType", "enabled", "expiration", "reason", "jitPolicy", "mode"}], "maxCount"}` — wraps `GET /api/v1/jit/customer/{customerId}`. No password/OTP field exists anywhere in the upstream `JitAccountItem` schema.
6. `cyberqp_list_tenant_jit_accounts(search_text: str | None, limit: int = 50, page: int | None)` → same item shape as #5, tenant-wide — wraps `GET /api/v1/jit/tenant`.
7. `cyberqp_check_jit_account(customer_id: str, user_type: str, agent_id: str | None)` → `{"exists": bool}` — wraps `GET /api/v1/jit/customer/{customerId}/account/check`.
8. `cyberqp_list_events(customer_id: str | None, account_id: str | None, event_type: str | None, status: str | None, start_date: str | None, end_date: str | None, limit: int = 50, cursor: str | None)` → `{"data": [{"id", "customerId", "customerName", "accountId", "technicianId", "technicianName", "technicianEmail", "eventType", "status", "title", ...}], "hasMore", "nextCursor"}` — wraps `GET /api/v1/event`.
9. `cyberqp_list_event_types()` → `{"data": [...], "totalItems"}` — wraps `GET /api/v1/event/types`.
10. `cyberqp_get_tenant_company_data()` → `{"data": {...}}` — wraps `GET /api/v1/tenants/company-data`.

All `limit` parameters default ≤ 50 and are server-side clamped to a hard cap of 200 (SOP §2.5); responses are serialized compact (`separators=(",", ":")`, `ensure_ascii=False`, no `indent=2`); any response that would exceed 20,000 characters is truncated with `has_more` set rather than returned whole.

**Deliberately not built** (credential-exposing and/or write; excluded from the tool surface entirely, per the ticket's own "hard-scoped" wording and SOP §2.7 "default only read"):

| Endpoint | Why excluded |
|---|---|
| `GET /api/v1/account/{accountId}/password` | Returns an account password. |
| `GET /api/v1/jit/customer/{customerId}/account/{accountId}/password` | Returns a JIT account's password. |
| `GET /api/v1/jit/customer/{customerId}/account/{accountId}/otp`, `POST .../otp`, `DELETE .../otp` | Return or set an OTP secret. |
| `POST /api/v1/jit/customer/{customerId}/account`, `DELETE .../account/{accountId}`, `PATCH .../enable`, `PATCH .../disable` | Create, delete, enable, or disable a JIT account — writes. |
| `POST /api/v1/identity-verification/self-serve-notification` | Triggers an identity-verification/MFA push — write/side-effecting. |
| `POST /api/v1/event` | Submits an event — write. |
| `GET /api/v1/tenants/install-token`, `GET /api/v1/customers/installer` | Return an agent enrollment token / installer download — treated as credential-equivalent and operational, not PAM "visibility". |
| `GET/POST /api/v1/auth/*` (`login`, `refresh-token`, `revoke-token`, `notification-engine-token`, `status`) | OAuth/session plumbing, not business data. Handled by the Connector gateway that injects the per-request header (see Key flow below); not exposed as an agent-facing tool. |

**Error mapping** (SOP §4.2): upstream `400`/`422` → `invalid_argument`; `401`/`403` → `unauthorized`; `404` → `not_found` (only for genuine single-resource-by-ID lookups — tools 2, 3, 4, 5, 7; list-root tools 1, 6, 8, 9, 10 return an empty `data` list on no matches, never `not_found`, per SOP §4.2 "an empty result is not an error"); `429` → `rate_limited` (`retryable=true`); `5xx` or timeout → `upstream_error` (`retryable=true`). `message` never includes the raw upstream response body (it may carry tenant-identifying detail beyond what the error needs).

### Key flow / sequence

1. The MSPbots Connector gateway (`connect.mspbots.ai`) obtains and refreshes the tenant's CyberQP OAuth2 access token out of band — per the Connector's own feature list, "OAuth tokens refresh automatically" — and injects it as `X-CyberQp-Access-Token` together with `X-CyberQp-Base-Url` on every `/mcp` request.
2. This server's auth middleware reads both headers into a request-scoped `ContextVar`. Either header missing → 401 naming the missing header(s), before any call to CyberQP (SOP §3.2).
3. The invoked tool builds the request against `{base_url}{path}` via `httpx.AsyncClient`, attaching `Authorization: Bearer <token>`.
4. The CyberQP response is mapped to the tool's trimmed JSON shape (§ Data & API contract) or to the error envelope; returned as a compact JSON string.
5. The `ContextVar` is reset in a `finally` block regardless of outcome (SOP §3.3); nothing is cached across requests (SOP §3.4) — CyberQP tokens expire hourly, so caching would be actively wrong, not just risky.

### Non-functional

- **Concurrency/isolation**: pure read pass-through with no local state; per-request credential isolation via `ContextVar`, no global or module-level credential storage (SOP §3.3–3.4).
- **Performance**: this server never auto-paginates to fetch "all" records on the agent's behalf — the caller pages explicitly via `cursor`/`page` plus `hasMore`/`nextCursor` (or `maxCount` for the small, fixed-size JIT-policy/JIT-account lists).
- **Security**: credentials are read only from headers, never persisted, never logged (SOP §6/§11 — a `gitleaks` scan runs at the dev gate). The tool inventory itself is the security boundary: no code path in this server can retrieve a credential or mutate CyberQP state even in the presence of a future bug, because no such endpoint is ever called. Multi-tenant isolation is inherited from CyberQP's own per-token scoping; this server adds request-level isolation on top (no cross-tenant data can leak through a shared in-process cache because there is no cache).
- **Observability**: standard access logging — method, tool name, HTTP status, duration — never header values or response bodies (SOP §6).
- **Rate limits**: CyberQP's own API-level limits apply; `rate_limited`/`retryable=true` is the only accommodation at this layer (no local rate limiting added — not justified without an observed need).

### Risks & dependencies

- **Risk 1 (non-blocking)**: the exact accepted values for `directoryType`/`accountType`/`userType` are not fully enumerated in the fetched OpenAPI snapshot (typed `string`, not a closed `enum`) — see Open Question Q1. The dev leg confirms against the live spec or CyberQP's docs at implementation time.
- **Risk 2 (non-blocking)**: CyberQP serves three regional hosts; this design was verified against the CA host's spec only. The US/EU hosts are documented by CyberQP to serve the same shape under the same paths, but that has not been checked byte-for-byte. Mitigated by making the base-URL header required rather than guessed (Decisions below); if a region genuinely diverges, it would surface as an `upstream_error`/`not_found` at runtime, not a silent wrong answer.
- **Dependency**: none. Fully additive; does not depend on any other in-flight ticket, and does not touch the MCP gateway or control plane (no gateway change needed — this is a pure vendor connector).

### Decisions made by DEV01

(Per `mcp-track.md` §2.4 — choices made without anyone to ask, posted separately as `[DESIGN DECISIONS · PRD-21228]` after the `[DESIGN]` stub.)

- **Stack**: Python + FastMCP + httpx + pydantic over Node/TypeScript. Why: matches the SOP's own reference implementation and the stack already used by sibling repos in the org; alternative (TypeScript) carries no project-specific advantage here.
- **Excluded endpoints are not built at all, not built-and-flagged-off**. Why: the ticket's own wording is "hard-scoped to read-only, non-credential-exposing tools" — a feature flag is still a code path that could be flipped on by a future change; not implementing the endpoint is the only form of "hard" scoping. Alternative considered: implement them behind a default-off flag for future extensibility; rejected for the reason above.
- **`X-CyberQp-Base-Url` is required, with no default host**. Why: CyberQP tenants are split across three regional hosts with no way to infer the correct one from the access token alone; a wrong silent default (e.g. always `us.getquickpass.com`) would fail in a way that could look like "a region's data is empty" instead of "wrong region entirely". Alternative considered and rejected: default to the US host.
- **`cyberqp_check_jit_account` kept as its own tool** despite overlapping with `cyberqp_list_customer_jit_accounts`. Why: it is a direct 1:1 wrap of a cheap existence-check endpoint CyberQP already offers; dropping it would force the agent into an extra list-then-filter round trip for a yes/no question. Alternative considered: drop it, let the agent filter a list result; can still be removed later if usage data shows it's never called standalone.
- **No further tool merging beyond the 1-tool-per-distinct-query-shape baseline**. Why: 10 tools is well under the SOP's "≤ 20" guideline, so there was no pressure to collapse further; each tool maps to a genuinely different CyberQP path/parameter shape.

To change any of these, say so in a comment and move the ticket back to `5b - ready for groom`.
